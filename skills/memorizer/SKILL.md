分析已完成的任务，将值得保留的知识写入对应的记忆层。

## 依赖

- **Skills**: `knowledge-synthesis`, `obsidian-markdown`

## 先判断：是否值得记录

只有满足以下条件之一才继续，否则直接报告"无需记录"并结束：

- 涉及非显而易见的架构决策或约束（why 不直观）
- 发现了坑 / 反模式 / 踩过的雷（其他人会再踩）
- 项目特定的可复用模式（不是通用的最佳实践）
- 用户明确表达的偏好或纠正
- 项目结构的关键变化

## 三层记忆

### 1. 用户偏好 — `~/.talos/profile.md`

- **内容**: 跨项目的编码风格、协作习惯、工具偏好
- **限制**: ≤50 行。满了删不重要的，为新内容腾空间
- **格式**: 纯文本要点列表

### 2. 项目热记忆 — `wiki/hot.md`

- **内容**: 影响后续所有工作的关键约束、重大坑、项目级强偏好
- **限制**: ≤100 行。满了删不重要的，为新内容腾空间
- **格式**: 纯文本要点列表

### 3. 项目知识库 — `wiki/<category>/<name>.md`

- **内容**: 特定领域知识、可复用模式、技术选型记录
- **格式**: Obsidian markdown，含 `[[wikilinks]]` 链接相关页面
- **索引**: 更新 `wiki/INDEX.md`，每条一行摘要

## 流程

1. 回顾任务：PRD、代码变更、review 结果、执行中的关键发现
2. 判断是否有值得记录的内容（如无，直接结束）
3. 判断写入哪一层（用户偏好 / 热记忆 / 知识库）
4. 读取目标文件，检查是否已有相关内容可更新
5. 加载 `obsidian-markdown` skill 格式化知识库页面
6. 写入或更新对应文件
7. 若写入知识库，更新 `wiki/INDEX.md`

## 什么不该记

- 任何合格开发者都知道的常规实现细节
- 可从代码 / git history 推断的内容
- 一次性的调试细节（除非揭示了系统性问题）
- 与项目无关的通用知识
- 纯粹的事实陈述（没有 why 或教训）
